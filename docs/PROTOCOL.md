# Сетевой протокол игры «Крестики-нолики» (черновик v0)

Статус: **черновик для согласования с командой**. Пока ничего из этого не реализовано.
Автор раздела `session`. Файл предлагается положить в репозиторий как `docs/PROTOCOL.md`.

## 1. Зачем этот документ

Цель проекта включает онлайн-игру по частной сети. Чтобы три части проекта (`core`, `session`, `gui`)
не разошлись, заранее фиксируем: кто главный, какие сообщения ходят между игроками и что от этого
требуется от каждой части.

## 2. Роли

- **Хост**: тот, кто создал игру. У него работает настоящий `GameSession` со всеми правилами
  (`GameRules`). Хост **единственный решает**, валиден ли ход. Это исключает рассинхронизацию.
- **Клиент**: тот, кто подключился. Отправляет свои ходы и показывает состояние, которое прислал хост.
  Клиент **не меняет своё поле сам**, пока хост не подтвердил ход сообщением `move_applied`.

Хост тоже играет (за себя ходит его GUI). Удалённый соперник у хоста представлен как `RemotePlayer`,
реализующий `IPlayer`, и его ходы проходят через тот же `applyMove`.

## 3. Транспорт и формат

- TCP. Порт по умолчанию: 45454 (предложение, настраивается).
- Одно сообщение = **одна строка JSON в UTF-8**, оканчивающаяся символом `\n`.
  (TCP это поток байтов, без явного разделителя сообщения склеиваются или режутся.)
- Максимальная длина строки: 4096 байт. Более длинная строка считается ошибкой, соединение закрывается.
- Поле `type` обязательно в каждом сообщении. Неизвестные поля игнорируются (чтобы протокол можно было
  расширять), неизвестный `type` даёт ответ `error`.
- Версия протокола: целое число, сейчас `1`.
- Шифрования и аутентификации нет: протокол рассчитан на частную сеть.

## 4. Установка соединения

1. Клиент подключается по TCP и отправляет `hello`.
2. Хост проверяет версию. Если версия не совпадает, отвечает `error` (код `version_mismatch`) и
   закрывает соединение. Иначе отвечает `welcome`.
3. После `welcome` игра стартует: первым ходит X.

Пока партия идёт, новые подключения отклоняются ответом `error` с кодом `game_in_progress`
и закрываются. Исключение: подключение с верным `resumeToken`. Токен доказывает, что это тот же
игрок, поэтому такое подключение заменяет прежнее, даже если хост ещё не заметил, что старое
пропало (раздел 11).

Переподключение после разрыва описано в разделе 11. В `welcome` хост выдаёт клиенту секретный
`resumeToken`, по которому клиент потом докажет, что он тот же игрок.

## 5. Выбор стороны

Хост в настройках создаваемой игры выбирает: **X**, **O** или **случайно**. При «случайно» жребий
бросает хост в момент старта. Результат клиент узнаёт из поля `yourSymbol` в `welcome`.
Клиент ничего не выбирает и не бросает. Первым всегда ходит X.

## 6. Нумерация ходов

Каждый подтверждённый ход получает порядковый номер `moveNo` (1, 2, 3...). Номер нужен, чтобы
отличать устаревшие запросы (например, запрос отмены) от актуальных.

## 7. Сообщения

### Клиент → хост

| type | поля | назначение |
|---|---|---|
| `hello` | `protocol`, `resumeToken` (необязательно) | начать подключение; токен указывается только при переподключении |
| `move` | `row`, `col` | мой ход |
| `undo_request` | `moveNo` | прошу отменить мой последний ход |
| `undo_response` | `moveNo`, `accept` | ответ на запрос отмены от соперника |
| `restart_request` | | прошу начать партию заново |
| `restart_response` | `accept` | ответ на запрос перезапуска от соперника |
| `ping` / `pong` | | проверка живости соединения |
| `bye` | | аккуратный выход |

### Хост → клиент

| type | поля | назначение |
|---|---|---|
| `welcome` | `protocol`, `mode`, `yourSymbol`, `resumeToken` | принять и настроить игру |
| `sync` | `board`, `currentPlayer`, `moveCount`, `gameOver`, `winner` | полное состояние партии (после переподключения) |
| `move_applied` | `moveNo`, `player`, `row`, `col` | подтверждённый ход (чей угодно) |
| `move_rejected` | `reason` | ход не принят |
| `undo_request` | `moveNo` | соперник (хост) просит отмену своего хода |
| `undo_applied` | `movesLeft` | отмена выполнена, в истории осталось столько ходов |
| `undo_declined` | `moveNo` | отмена отклонена или устарела |
| `game_over` | `winner` | партия окончена |
| `restart_request` | | хост просит начать партию заново |
| `restart_applied` | `yourSymbol` | перезапуск согласован, партия началась заново |
| `restart_declined` | | перезапуск отклонён |
| `ping` / `pong` | | проверка живости соединения |
| `error` | `code`, `text` | прочие ошибки |

`undo_request` / `undo_response`, `restart_request` / `restart_response` и `ping` / `pong`
двунаправленные: запросить отмену или перезапуск может любая сторона, пинговать тоже.

### Примеры

```json
{"type":"hello","protocol":1}
{"type":"welcome","protocol":1,"yourSymbol":"O","resumeToken":"9f3c1a7e",
 "mode":{"name":"Classic","boardSize":3,"winLength":3,"misere":false}}
{"type":"move","row":1,"col":2}
{"type":"move_applied","moveNo":1,"player":"X","row":1,"col":2}
{"type":"move_rejected","reason":"not_your_turn"}
{"type":"undo_request","moveNo":5}
{"type":"undo_response","moveNo":5,"accept":true}
{"type":"undo_applied","movesLeft":4}
{"type":"game_over","winner":"X"}
{"type":"game_over","winner":null}
{"type":"hello","protocol":1,"resumeToken":"9f3c1a7e"}
{"type":"sync","board":"X.O.X....","currentPlayer":"O","moveCount":3,
 "gameOver":false,"winner":null}
{"type":"restart_applied","yourSymbol":"X"}
{"type":"ping"}
```

(Каждое сообщение на самом деле занимает одну строку, здесь одно из них перенесено для читаемости.)

`board` в `sync` это строка из символов `X`, `O` и `.` (пустая клетка): клетки по строкам доски,
слева направо, сверху вниз. Так сообщение компактнее, и доска до 60x60 помещается в лимит длины строки.

Значения `reason` в `move_rejected`: `not_your_turn`, `invalid_cell`, `game_over`.

Коды в сообщении `error`: `version_mismatch` (версии протокола не совпали), `game_in_progress`
(партия уже идёт), `game_finished` (партия уже окончена), `unknown_session` (токен неизвестен),
`bad_message` (сообщение не удалось разобрать), `unexpected_message` (сообщение не
соответствует моменту или направлению). После `error` при подключении хост закрывает соединение.
`winner` в `game_over`: `"X"`, `"O"` или `null` (ничья). В режиме *misere* это **победитель партии**,
то есть тот, кто НЕ построил линию (определяет `GameRules::winner`).

## 8. Ход игры

1. Игрок, чья очередь, отправляет `move` (хост ходит локально).
2. Хост проверяет ход. Если ход допустим, рассылает `move_applied` (и себе, и клиенту).
   Если нет, отвечает отправителю `move_rejected`.
3. Если ход завершил партию, после `move_applied` хост отправляет `game_over`.

## 9. Отмена хода

Правила:

1. Отмену можно запросить **только для своего последнего хода**, и только пока последний ход в истории
   принадлежит запросившему (то есть соперник ещё не сходил).
2. В запросе указывается `moveNo`. Если к моменту обработки последний ход уже другой, хост отвечает
   `undo_declined` (запрос устарел).
3. Соперник-человек должен **подтвердить** (`undo_response` с `accept: true`). Отказ даёт
   `undo_declined`.
4. После подтверждения откатывается **ровно один ход**, очередь возвращается запросившему,
   хост рассылает `undo_applied`.
5. Пока запрос отмены ждёт ответа, новые ходы не принимаются (`move_rejected`, причина `not_your_turn`).

## 10. Что требуется от частей проекта

### `core` (правила)

- `GameRules::winner(board)` возвращает **победителя партии**; в режиме *misere* это соперник того,
  кто построил линию. Проверяет всю доску целиком (не только последний ход), учитывает `winLength`
  и все четыре направления.
- `GameRules::isDraw(board)`: доска полна и победителя нет.
- Функции не изменяют доску и безопасны для многократного вызова (ИИ вызывает их тысячи раз).
- `GameMode` пересылается по сети как есть, менять его не нужно.

### `gui`

- Экраны сетевой игры: создать игру (выбор X / O / случайно, порт), подключиться (адрес, порт),
  ожидание соперника.
- `IGameObserver` будет **расширен** новыми событиями (запрос отмены или перезапуска от соперника,
  соперник отключился с таймером ожидания, соперник вернулся, партия прервана, ошибка, отказ в ходе).
  Конкретный список согласуем отдельно до реализации.
- GUI должен принимать события в любой момент, не только в ответ на клик: ответ соперника приходит
  асинхронно.

### `session`

- Асинхронный `IPlayer`, `RemotePlayer`, расширение `SessionConfig` и `IGameObserver`,
  операция «откатить ровно один последний ход».

## 11. Разрыв соединения и переподключение

Решение: **даём время на переподключение**.

1. Разрыв обнаруживается либо ошибкой TCP, либо по тишине (раздел 12).
2. Хост ставит партию на **паузу** и ждёт возвращения клиента **60 секунд** (значение настраиваемое).
   Пока пауза, ходы не принимаются, незавершённые запросы отмены и перезапуска сбрасываются.
3. Клиент в это время сам пытается подключиться заново к тому же адресу. При успехе он отправляет `hello`
   с `resumeToken` из первого `welcome`. Хост сверяет токен, отвечает `welcome` и затем `sync` с полным
   состоянием партии. Клиент заменяет своё состояние присланным, и игра продолжается.
4. Если за 60 секунд клиент не вернулся, партия **прерывается без победителя**.

Схема работает при обрыве сети с любой стороны, пока на машине хоста запущена программа. Если программа
хоста закрыта, состояние партии потеряно (оно хранится только у хоста), и повторные попытки клиента
закончатся прерыванием партии по таймеру.

`resumeToken` это случайная строка, которую хост генерирует при `welcome` и держит в памяти.
Он нужен, чтобы в игру не мог вмешаться посторонний, подключившийся в паузе.

## 12. Проверка живости соединения

TCP не замечает тихого обрыва (выдернутый кабель, отключившийся Wi-Fi) очень долго, иногда минутами.
Без проверки нельзя отличить «соперник думает» от «соперника нет», а раздел 11 как раз зависит от
быстрого обнаружения разрыва.

- Каждая сторона отправляет `ping` раз в **5 секунд**, получатель отвечает `pong`.
- Если от соперника ничего не приходило (ни сообщений, ни `pong`) **15 секунд**, соединение считается
  потерянным, и запускается процедура из раздела 11.
- Любое полученное сообщение сбрасывает таймер, так что во время активной игры пинги почти не нужны.

## 13. Перезапуск партии

Требует **согласия соперника**, по тому же принципу, что и отмена хода: `restart_request`,
затем `restart_response` с `accept`. При согласии хост рассылает `restart_applied` и запускает партию
заново **с обменом сторон**: тот, кто играл за X, становится O, и наоборот. Новый символ каждого
приходит в поле `yourSymbol` сообщения `restart_applied`. Новый жребий не нужен. При отказе:
`restart_declined`.

## 14. Имена игроков

Имена по сети **не передаются**. Профилей игроков нет.
Каждый игрок при желании вводит своё имя у себя в GUI и видит его на своём экране; соперник на
экране обозначается нейтрально («Соперник», либо по символу X / O). Протокол имён не знает,
игрок опознаётся только по `resumeToken` (раздел 11).

## 15. Принятые решения

1. Время на переподключение есть: 60 секунд, партия на паузе (раздел 11).
2. Если клиент не вернулся, партия прерывается **без победителя** (раздел 11).
3. Проверка живости через `ping` / `pong` включена в протокол (раздел 12). Реализуем позже,
   но формат фиксируем сейчас.
4. Перезапуск партии требует согласия соперника, стороны при этом меняются местами (раздел 13).
5. Имена по сети не передаются (раздел 14).

Остаётся уточнить при реализации: числа 5 / 15 / 60 секунд подобраны на глаз, они должны быть
настраиваемыми.
